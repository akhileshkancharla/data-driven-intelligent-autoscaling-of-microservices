# Intelligent Autoscaling of Microservices

A Shiny demonstration built from **real trace data**. Forecasts are fitted with `rpart`; fixed, reactive, and predictive scaling outcomes are **simulations**. No Kubernetes Pods are created, and the replay does not estimate measured latency or service-time changes.

## Run

From the project directory, with R on PATH and `shiny` and `rpart` installed:

```powershell
Rscript app.R --prepare
Rscript -e 'shiny::runApp(".", launch.browser=TRUE)'
```

To install the packages once: `Rscript -e 'install.packages(c("shiny","rpart"), repos="https://cloud.r-project.org")'`. On the machine used to build this project, R and Shiny were installed under the original Codex workspace rather than on PATH; the app itself is portable. The supplied `selected_service.csv`, `forecast_model.rds`, and `test_metrics.csv` were generated by the preparation command. The app uses the saved model without retraining on startup.

## Data and method

Source: Mehran et al., *A trace of microservice time, call rate, and number of replicas*, Zenodo v3 (2024), DOI [10.5281/zenodo.14245634](https://zenodo.org/records/14245634), derived from Alibaba 2021 microservice traces. `dataset-replica-mcr-mt.csv` is the 8.2 MB file from that record (MD5 `148f0b2c9fc14bf65a25ae8d7ef3786b`), not the full trace. It has **no header**. The seven columns are interpreted from the record as first timestamp, second timestamp, service ID, container ID, reported replica count, service time, and call rate. The source does not explicitly define the call-rate or service-time units, nor the exact meaning of the first timestamp, so the app labels values as source call-rate units and uses elapsed minutes from the second timestamp.

The record says 30-second intervals, but the second timestamp in this file advances by **60,000 units** between adjacent observations. Assuming those units are milliseconds, the observed cadence is one minute. The app forecasts the next observed point, 60 seconds ahead; it does not create artificial 30-second samples.

Repeated `(service ID, second timestamp, container ID)` rows are collapsed with a median. For each service/timestamp, the median of distinct container call-rate values is used. This avoids summing a service-level rate repeated across containers. The original trace does not settle whether each container's call-rate value is service-level or container-level; this conservative aggregation is a **proxy**, not an independently validated total service throughput. Reported replica counts are medians for context only. Missing minute buckets are never filled. The selected service is the one with the longest contiguous, nonconstant one-minute run of at least 20 buckets, with ID order breaking ties.

The selected service is `99f2e7b501f50db9b4089242a5d3e1aba334c32e0c718b8d79281529a9489b15`: **129 observed minute buckets** from 784 distinct container/time observations (1,583 raw rows). Features at time *t* are current and three prior call rates, a three-point trailing average, and recent growth. The target is the call rate at *t + 1 minute*. Forecast origins are split chronologically 60%/20%/20% into train/validation/test (75/25/25). Validation selects the tree complexity; the final `rpart` model fits train plus validation, then test is evaluated once. Persistence predicts the current value. No future traffic, replica count, service time, or invented event label enters the model.

On the 25 held-out test origins, `rpart` has MAE **5.8953** and RMSE **7.6174**; persistence has MAE **4.8298** and RMSE **6.1731**. These are observed test results in source call-rate units. Persistence performs better in this run.

Replica recommendations use `ceiling(forecast * safety_factor / capacity_per_replica)` clamped to user-set min/max. Capacity is a **heuristic chosen for presentation**, not measured per-replica capacity. Replay counts overload when observed call rate exceeds simulated replicas × heuristic capacity; replica-minutes and scaling actions are likewise simulated. Startup delay is in observed one-minute steps.

The **Load observed rise** button resets the controls and window around the largest measured one-step rise within the held-out test segment (elapsed minute 125 to 126). RL/PPO and live Kubernetes control are future extensions.
